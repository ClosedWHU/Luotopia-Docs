本指南规定 Luotopia 项目文档的语言风格、结构组织与排版要求。所有 PR 提交的文档变更均需符合本指南。

## 1. 语言风格与基调

### 1.1 专业性

- 禁用口语化修饰词：不使用「实战版」「技术干货」「避雷针」「点我直达」等非正式表述。
- 中性叙事：不使用第一人称（如「我觉得」「我建议」），改用客观叙事（如「系统设计采用……」「建议配置为……」）。
- 准确定义：技术术语与源码保持一致。

### 1.2 简洁性

- 杜绝冗余：标题与正文不使用情绪化词汇（如「炸裂」「深度分析」）。标题直接反映内容，写「系统架构分析」，不写「深度解析系统架构干货」。
- 直接切入：每篇文档在第一段说明它解决的问题或描述的对象，不做多余的背景渲染。

### 1.3 标点与用词

- 中文正文使用全角标点（：，。「」）；代码、字段名与配置键保留原文。
- UI 元素与术语引用使用直角引号「」，嵌套时使用『』，不使用直引号 `""` 或弯引号。
- 省略号写作「……」，破折号写作「——」。
- 中英文、中文与数字之间加一个半角空格；半角英文数字与全角标点之间不留空格。
- 同一概念全站使用同一术语：两套账户体系统一用「账户」（武大账户 / 珞家账户）；「其它」统一写作「其他」；校车统一写作「校巴 / 校园巴士」。第三方系统原文、端点名与代码标识（如 `social-accounts`）保留原文。
- FAQ 问句统一写作 `**Q：问题**`，冒号用全角。

## 2. 文档结构规范

每篇技术文档尽可能遵循以下逻辑层次，禁止采用「前言 + 补丁」的结构。小节按内容取舍，不为对称立空节；无内容的层级直接省略。

1. 概览：描述该组件或模块的功能边界、核心目标，以及与系统其他部分的关系。
2. 设计原理：阐述为什么要这样设计，包含核心算法、协议选择或架构考量。
3. 技术实现：提供源码级分析、流程图、配置示例或 API 定义。
4. 最佳实践与约束：
    - 融合叙事：把开发中的经验教训直接写进正文的逻辑流程。
    - FAQ 机制：针对常见的配置误区或集成难点，在重点章节末尾提供 FAQ 列表。

## 3. 开源文档站与闭源代码

文档站公开、业务代码闭源时，深度控制见[公开文档边界](./public_docs_policy.md)。

摘要：写契约、边界、目录约定；不写**密钥、可复现逆向、未公开接口、完整闭源实现**。

## 4. 排版与格式要求

### 4.1 标题层级

- front matter `title` 是唯一标题来源；正文**不写** `# H1`。站点以 `title` 渲染页首 H1，避免双重声明漂移。
- 使用 `## H2` 与 `### H3` 分层，标题嵌套不超过四级。
- 标题内不使用 `**加粗**` 等行内标记；多文件分区内不使用跨文件连续编号（如上一文件编到 4，下一文件从「4.5」起）。

### 4.2 代码块与引用

- 语言标记：所有代码块**必须**指定语言（如 `bash`、`go`、`javascript`）；无高亮需求的纯文本使用 `text`。
- 告警框：使用 GitHub 风格告警语法。站点已装 `remark-github-blockquote-alert`，GitHub 网页阅读时同样生效。合理使用以强调关键信息。
    - `> [!NOTE]`：背景信息。
    - `> [!IMPORTANT]`：必须遵守的操作。
    - `> [!CAUTION]`：可能导致数据丢失或安全风险的操作。
    - 使用 Docusaurus 原生 `:::` 语法时：本站启用 `future.v4`，自定义标题必须写成方括号形式（如 `:::note[标题]`）；`:::note 标题` 会整块渲染为字面文本。
- 引用块不写作裸提示（`> 注意：`、`> 说明：`、`> 本文说明`），改用上述告警语法。
- 列表项不以 `- **名词**：` 的机械形态开头；加粗只用于警示、危险操作、硬性约束与关键结论。

### 4.3 链接、命名与 URL

- 引用项目内其他文档时使用相对路径（含 `.md` 扩展名）。
- 引用源码文件时指向具体路径，并简要说明其职责。
- 文件名使用 `snake_case`；公开 URL 使用 kebab-case：多词文件在 front matter 声明 `slug: kebab-name`，旧下划线 URL 由 `docusaurus.config.ts` redirects 兜底。
- 跨分区链接使用 `pathname:///server/...` 形式，并以 slug 化后的 kebab URL 为准。

## 5. 反面案例对照

| 错误示例 | 推荐修改 |
|------|------|
| `### 2.4 技术干货：从 AI 置信度到风险评分` | `### 2.4 AI 风险评分机制与阈值设计` |
| `## 5. 开发建议与避雷针` | `## 5. 最佳实践与常见集成难点` |
| `# 业务接口调用指南 (实战版)` | `# 业务接口调用规范` |
| `- **干货**: 允许我们精准定位...` | `- 实现价值：该监控项支持精准定位……` |
